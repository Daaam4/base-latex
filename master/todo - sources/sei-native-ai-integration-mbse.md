# Native AI Integration for Model-Based Systems Engineering: Three Layers that Make It Work

## Topic
A controlled experiment with a reported design, arms, task counts and quantitative outcomes — the only published controlled SysML v2 agent-tooling benchmark found to date, functioning as a technical report despite the blog venue (central example for the exposé's "non-scientific sources" justification). Three-layer architecture: (1) an AI coding assistant (model/vendor-agnostic; VS Code + Claude Code / OpenAI Codex / Continue against the same repo/tools), (2) a language-aware modeling toolchain — Sensmetry's **Syside** (SysML v2 language server) for interactive LSP support plus a noninteractive `syside check` CLI that both assistants and CI call, sole authority for syntax/semantic diagnostics, and (3) a knowledge/workflow layer — a version-controlled Markdown knowledge base exposed through a repository-local **MCP server** with stable topic-based retrieval tools (explicitly *not* an LLM or knowledge graph, just curated-document retrieval) plus 10 file-based **skill** definitions (`knowledge-primer-sysml`, `model-sysml`, `fix-sysml`, `review-sysml`, `analyze-sysml`, `explain-sysml`, `reverse-engineer-sysml`, `views-sysml`, `codegen-sysml`, `docgen-sysml`) that encode retrieve→edit→check workflows.

## Method
Three arms, same 8 tasks, two scales, one model (Claude Opus 4.6): (i) baseline — single-pass generation, no tools; (ii) CLI-only — generation + `syside check` feedback loop, no knowledge/skills; (iii) full tooling — + MCP knowledge server + skills, same validation loop. n=40 small-task outputs, n=24 large-task outputs per arm. Quality measured via a project-defined "pattern measure" (29 measures: structure/richness/connectivity, traceability/patterns/organization, task-specific acceptance), 0–100.

**Results:** Baseline 3.7 errors/100 lines (small), 25.6 (large); CLI-only and full tooling reach 0 errors/warnings at both scales — the validation loop eliminates syntax errors entirely. Pattern measure: baseline 78.3, CLI-only **71.7** (slightly *worse* — validation alone doesn't help modeling quality), full tooling **94.1** on large tasks — curated knowledge/skills, not the validator, drive the quality gain. Token cost scales sharply with tooling: ~59K (baseline) → 106K (CLI-only) → 143K (full tooling) on large tasks.

**Worked example** (4-drone aerial survey swarm, full-tooling arm): 8 coordinated files, 3186 lines, 0 validator errors after 2 iterations, 97.2/100 pattern score — but manual review found the model's separation distances (30 m/10 m) and lost-link timing (3 s + 60 s loiter) **do not match the prompt** (50 m/20 m, 30 s), several requested components are missing, and analysis/verification blocks are structurally present but **not executable/evaluated** (no bound calculation results, no verdict expressions). Paper's own strongest quote for the "syntactic validity ≠ semantic/engineering correctness" argument: *"A clean validation run therefore shows only that the model passes the tool's syntax and semantic checks."*

## Relevance
- **Supports H2** directly: tool design (validation alone vs. validation + curated knowledge) measurably shifts capability boundaries, with a clean separation of *which* layer buys *which* gain (syntax vs. modeling-pattern quality) — close to the exact ablation logic in `04-evaluation-design.md`.
- **Direct methodological template**: the thesis's 3-arm design (no tool / thin bridge / semantic bridge) mirrors this paper's arms one-to-one.
- **Precedent for single-model evaluation** (Claude Opus 4.6 only) → supports D9 (Claude-only) as a defensible, precedented choice; also precedent for stating it as a threat to validity.
- **The 4-drone worked example is a ready-made illustration** for this thesis's "collateral damage" / "silent semantic drift" failure category — a model that validates cleanly while silently deviating from the stated requirement.
- **Differentiation:** entirely file-based (textual notation + Syside LSP/CLI, version-controlled Markdown + MCP-served retrieval). No industrial modeling tool, no live in-session model state in a running MBSE server, no tool-native validation/evaluation beyond a language-server check, no graph traversal. This thesis works against a **live model inside MSoSA**, and its MCP server is a retrieval-only service, not a model-editing/model-repository interface — sharpens the "thin CRUD bridge vs. semantic bridge with tool-native validation" distinction this thesis tests.
